# Rio v0.10.1

**`rio record inspect` shows the digest of what was uploaded, licence expressions match SPDX ids in any case, and the BSI profile's errors say more precisely how to fix them.**

`rio record inspect` printed an empty digest and zero bytes for every uploaded SBOM, because the
receipt records it as a reference to the run's output rather than repeating the digest. Here is the
same synthetic run from the README's example
([`tools/demo-use-case`](https://github.com/rebaze/rio/blob/v0.10.1/tools/demo-use-case)), delivered to
a **synthetic** Dependency-Track receiver on loopback. The v0.10.0 line is from the run committed in
`tools/demo-use-case/example`; the v0.10.1 block is the delivery section of the same demo run with
a build of this release's source.

v0.10.0:

```text
  submitted role=sbom mediaType=application/vnd.cyclonedx+json artifactOutput=payments-api sha256= bytes=0
```

v0.10.1:

```text
payments-api → security (http://127.0.0.1:62483): accepted
  project={"name":"payments-api","version":"2.3.0"} transport=http TLS=not recorded verification=not-applicable
  submitted role=sbom mediaType=application/vnd.cyclonedx+json artifactOutput=payments-api sha256=7360e0f24171599b96af5e337a772c510b007e33f700fedf306352d7b6081262 bytes=4642
  acknowledgment=accepted HTTP=200 code=accepted TLS=not recorded
    dependency-track:event-token: 5d1f9a9e-2f0c-4c55-9d8e-7c3b2a1f0e64
  project fields readBack=read
    tags requested=["owner:payments"] state=observed
```

The digest is the one in the receipt's `output` line, so you can match the upload to the SBOM in the
run directory. Receipts written by v0.10.0 already hold this information; v0.10.1 reads them the
same way.

## What changed

- **`record inspect` resolves submitted outputs** ([#218](https://github.com/rebaze/rio/issues/218)).
  A submitted body that names an artifact output now shows that output's digest and size.
- **SPDX ids in licence expressions match regardless of case** ([#189](https://github.com/rebaze/rio/issues/189)).
  SPDX matches identifiers case-insensitively, so a concluded expression such as `apache-2.0` or
  `mit OR APACHE-2.0` now satisfies `distributionLicences` under the BSI TR-03183-2 profile.
  `license.id` and `dataLicense` still need the list's exact spelling, because CycloneDX's schema
  enumerates them; `dataLicense: cc0-1.0` is now refused with `must be spelled "CC0-1.0"`. See
  [Requirement profiles](https://github.com/rebaze/rio/blob/v0.10.1/docs/manifest.md#requirement-profiles).
- **The distribution conflict names what changed** ([#189](https://github.com/rebaze/rio/issues/189)).
  Normalizing rio's own output again after the subject's version, manufacturer or licences changed
  failed with a bare `distributions cannot be replaced`. For a file component rio added, it now
  names the copied fields that differ, for example `its version ("1.4.0"; the subject's is
  "1.4.1") no longer matches the subject's, which it copies`. See
  [Build and source context](https://github.com/rebaze/rio/blob/v0.10.1/docs/context.md).
- **Better advice for file properties** ([#189](https://github.com/rebaze/rio/issues/189)).
  Components missing `filename`, `executable`, `archive` or `structured` now get the level advice
  `deployableHash` had, and it names both levels without file fields: `assembled` for a part built
  into another, `logical` for a product or grouping.
- **Stricter receipt checks** ([#189](https://github.com/rebaze/rio/issues/189)). A receipt's
  profile failure counts must fit the levels that demand each field, and `componentEvaluation`
  must agree with what was required, as `index.json` already enforced. Every receipt rio has
  written meets both.
- **A shorter README** that leads with a manifest, the invocation and the result
  ([#217](https://github.com/rebaze/rio/pull/217)).

## Release tooling

- The Change class and security auto-merge workflows run on `pull_request` instead of
  `pull_request_target`, which GitHub is starting to block by default
  ([#208](https://github.com/rebaze/rio/issues/208)).
- CI's Python 3.9 jobs run on `ubuntu-24.04`, since `ubuntu-latest` (26.04) has no Python 3.9.

## Compatibility

Manifests, receipts and the delivery are unchanged. An expression that v0.10.0 refused only for
its case now passes the profile.

# Rio v0.10.0

**Rio delivers an SBOM to Dependency-Track with its owner's fact sheet, routing tags, parent and latest-version flag, and records what the server actually applied.**

One `rio.yaml` now carries what a team used to add with `jq` and a second uploader. Enrichment writes
the issue tracker, release notes, advisories and labelled links, such as the application's fact sheet,
onto the SBOM subject. The Dependency-Track target sets the project's tags, parent and "latest version"
with the upload. A 200 does not say whether those applied, so Rio reads the project back and records
each value as `observed`, `different` or `unknown`, never as applied unseen.

Consumed → enriched: the subject of the enrichment demo's `console` SBOM after `rio`, trimmed to its
external references. The data is synthetic; the output comes from a binary built from this release's
source ([`tools/demo-enrichment`](https://github.com/rebaze/rio/blob/v0.10.0/tools/demo-enrichment)).
The `...` stands for the security-contact, support and website references.

    "component": {

Delivered → acknowledged: `rio record inspect` on a receipt from the project-fields demo
([`tools/demo-delivery/project-fields.py`](https://github.com/rebaze/rio/blob/v0.10.0/tools/demo-delivery/project-fields.py)).
The project version already existed with other tags, and the key lacks `PORTFOLIO_MANAGEMENT_UPDATE`,
so the receiver answered 200 and kept them. Rio says so. The receiver is **synthetic**: it imitates

`1.0.0` and then `1.1.0` reads back like this (`GET /api/v1/project/{uuid}`, trimmed to the
fields Rio set; the server's other fields and each tag's other properties are left out):

    {"type": "issue-tracker", "url": "https://example.com/rio-it-showcase/issues"},
    {"type": "other", "url": "https://ea.example.com/factsheet/Application/rio-it-showcase", "comment": "Fact sheet"},
    {"type": "release-notes", "url": "https://example.com/rio-it-showcase/releases"},

`1.0.0` lost the latest flag when `1.1.0` was created. Keep the three apart per application: the
fact-sheet link says who is responsible, an `owner:` tag routes findings to them, and
`securityContact` stays the public reporting channel.

## What changed

- **Subject links** ([#202](https://github.com/rebaze/rio/issues/202)). `enrichment.subject` gains
  `issueTracker`, `releaseNotes` and `advisories`, typed references validated like `website`. It
  also gains `links`: a list of `{label, url, type}` whose label becomes the reference's `comment`,
  with `type` defaulting to `other`. Each label is its own leaf, `subject.links[<label>]`. Shared and
  artifact lists merge per label, `replace` can name one label, and each label has its own change
  record and its own entry in `rio plan --json`. An existing link with the same type and URL is left
  alone; the same label with another URL is a conflict unless replaced. See
  [Links](https://github.com/rebaze/rio/blob/v0.10.0/docs/enrichment.md#links).
- **Dependency-Track tags, parent and latest version** ([#203](https://github.com/rebaze/rio/issues/203)).
  Dependency-Track targets and their per-artifact `overrides` accept `tags`, `parent` (`{uuid}`, or `{name}`
  with an optional `version` for version-less grouping parents,
  [#213](https://github.com/rebaze/rio/issues/213)) and `isLatest`. They are sent only when configured. Tags are the project's
  complete tag set. Parent and latest apply only when the upload creates the project version, so
  they need `autoCreate: true` and a name/version project. After an accepted upload, and on
  `delivery reconcile`, Rio reads the project back. The receipt's new `projectFields` records each
  requested value and its state. A missing parent fails as `parent_not_found`. `rio plan`,
  `rio delivery plan` and `record inspect` show the fields. See
  [Tags, parent and latest version](https://github.com/rebaze/rio/blob/v0.10.0/docs/delivery.md#tags-parent-and-latest-version)
  for what Dependency-Track 5.2.1 does per case and per permission.
- **Tested against Dependency-Track 5.2.1.** The integration harness runs 5.1.1 or 5.2.1. On 5.2.1,
  the existing adapter contract passed, and so did a permission matrix for the new fields and the
  links. CI runs both against 5.2.1 on every change ([#212](https://github.com/rebaze/rio/issues/212)). See the
  [integration evidence](https://github.com/rebaze/rio/blob/v0.10.0/tools/demo-delivery/integration/README.md#project-tags-parent-and-latest-version-on-521).

## Dependencies and release tooling

- `oras-go` 2.7.0 for OCI delivery, and `doublestar` 4.10.4, which now matches `artifactSets`
  patterns with `**` inside a brace alternative, such as `x{**/a,b}`, correctly. Neither is a
  security fix.
- Releases are published without a manual approval gate, and authored notes such as these are
  optional ([#199](https://github.com/rebaze/rio/issues/199)).

## Compatibility

Manifests without the new keys behave and produce output as before, and a Dependency-Track target
without `tags`, `parent` or `isLatest` sends exactly the same upload. Rio v0.9.x and older refuse
manifests that use the new keys, and cannot read receipts that carry `projectFields` or delivery
journals that carry project read-backs. Receipts keep `schemaVersion: 1`.

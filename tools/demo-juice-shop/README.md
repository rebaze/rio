# Juice Shop: build → SBOM → Rio → delivery receipt

See the result before running the build: [backend receipt](example/backend-record.json),
[backend HTML report](example/backend-report.html), [frontend receipt](example/frontend-record.json),
and [frontend HTML report](example/frontend-report.html).

These excerpts are actual `rio record inspect` output from **Rio 0.7.0** on
2026-10-01, using source-built Juice Shop 20.2.0 SBOMs and local Dependency-Track:

```text
Rio 0.7.0 — pipeline: success
  gate=pass mode=fail schema=pass findings=0
backend → security (http://127.0.0.1:52840): accepted
  acknowledgment=accepted HTTP=200 code=accepted TLS=not recorded

Rio 0.7.0 — pipeline: failed
  gate=fail mode=fail schema=pass findings=559
frontend → security (http://127.0.0.1:52840): unattempted
```

| Captured result | Backend | Frontend |
|---|---|---|
| Component entries checked | 689 | 672 |
| Quality findings | 0 | 559 |
| Delivery | Accepted, HTTP 200 with event token | Blocked before upload |

The supplier and example CI URL are **synthetic demo assertions**; the build,
SBOMs and receiver response are real. The receiver used loopback HTTP, so no TLS
was observed. A separate inventory check observed 654 backend components stored
and no frontend project. Acceptance and completed processing are separate facts.
Read the [capture provenance and offline inspection instructions](example/README.md).
Fresh dependency resolution can change the counts in your own run.

Build OWASP Juice Shop from source, generate its SBOMs with its own CycloneDX tools,
then use Rio to **add build context, check quality, and deliver to Dependency-Track**.
Finish by comparing a successful backend receipt with the frontend's quality-gate result.

You need Linux or macOS, Docker with Compose, Python 3.9+, and a browser. Allow several
GB of disk space and at least 4 GB of Docker memory. The first source build downloads
Node and npm dependencies and takes longer than subsequent Rio commands. Run these
steps in the same shell, starting at the root of this Rio checkout.

## 1. Choose your Rio binary

Use **Rio 0.7.0 or newer**. On macOS, install a release with Homebrew:

```sh
brew install --cask rebaze/tap/rio  # skip if already installed
RIO="$(command -v rio)"
```

On Linux, install a release into this checkout's ignored `target/` directory:

```sh
RIO_VERSION=0.7.0 RIO_INSTALL_DIR="$PWD/target/demo-bin" sh install.sh
RIO="$PWD/target/demo-bin/rio"
```

Or build Rio locally on either OS (requires Go):

```sh
make build
RIO="$PWD/rio"
```

Keep that choice for the rest of the walkthrough:

```sh
"$RIO" version
DEMO_SCRIPT="$PWD/tools/demo-juice-shop/demo.py"
DEMO="$(mktemp -d)/juice-shop"
```

## 2. Build Juice Shop and generate its SBOMs

```sh
python3 "$DEMO_SCRIPT" build "$DEMO"
cat "$DEMO/source.json"
```

Watch the actual git/npm build output. The helper clones Juice Shop **v20.2.0** at
commit `5658473cf8814459bf89000ce373b20ed0b4eb37` and builds it in a pinned Node 24
container. You do not need Node or npm installed on your machine, and Juice Shop's
web application is not started.

The build runs `npm install`, explicitly checks server compilation with
`npm run build:server`, then runs `npm run sbom`:

| Generated file under `$DEMO/source/` | What it describes |
|---|---|
| `bom.json` | Backend production dependencies, generated by `@cyclonedx/cyclonedx-npm` |
| `frontend/dist/bom/bom.json` | The production frontend bundle, generated by `@cyclonedx/cyclonedx-esbuild` during the install/build lifecycle |

These are [Juice Shop's own build scripts](https://github.com/juice-shop/juice-shop/tree/v20.2.0).
The helper copies their SBOMs into `inputs/` without editing them. It retains the
checkout, generated lockfiles and `build.log`; `source.json` records the actual commit,
Node/npm/generator versions, builder image/architecture, times and input hashes. Cypress's browser
binary is skipped because this walkthrough builds the app, not its browser tests.

For compatibility with Juice Shop's `stats.json` SBOM script, the demo pins Angular's
CLI/build tools to 22.0.1. The adjustment is saved in `build-overrides.patch`, and
Rio's source context honestly records the checkout as **dirty**. Application source
code is unchanged.

Upstream disables lockfiles by default; this build enables and retains them. The
source and builder are pinned, but a fresh install still resolves upstream version
ranges. Inspect your actual counts rather than expecting the published archive's counts.

## 3. Start the local receiver and inspect the pipeline

```sh
python3 "$DEMO_SCRIPT" prepare "$DEMO"
cd "$DEMO"
. ./demo.env
cat login.txt
cat rio.yaml
cat pipeline.json
"$RIO" plan --artifact backend
```

Open the printed browser URL and sign in using `login.txt`. This is a dedicated local
Dependency-Track instance; `demo.env` and `login.txt` hold its private credentials.
`rio.yaml` connects your generated inputs, enrichment, quality policy and receiver.
`pipeline.json` binds the actual source revision and local build ID to the new SBOM
hashes. The supplier and example CI URL are **demo assertions**; no upstream CI run
is claimed. Rio preserves existing upstream identities and dependency inventories.

The receiver uses explicit **HTTP on loopback**, and the receipt says so. Its feed
scheduler is disabled for predictable startup: this demonstrates SBOM handling, not
a vulnerability scan.

## 4. Enrich and deliver the backend

```sh
"$RIO" --artifact backend --receipt backend-record.json
"$RIO" record inspect --file backend-record.json
python3 "$DEMO_SCRIPT" status "$DEMO"
"$RIO" record report --file backend-record.json --output backend-report.html
```

The first command is the whole Rio pipeline: consume your generated SBOM, add the
supplier/build context, check required names/versions/package URLs, and upload the
result. Expect exit 0 and an accepted HTTP response with an event token.

In Dependency-Track, open **Projects → juice-shop → 20.2.0 → Components**. The helper
waits for receiver inventory separately; HTTP acceptance alone does not prove that
processing finished. Its inventory count can differ from Rio's count of source entries.

Open `backend-report.html` (`open backend-report.html` on macOS, `xdg-open
backend-report.html` on a Linux desktop). Show the input/output hashes, exact metadata
changes, passing checks, receiver/project and acknowledgment. Generated SBOMs and
`index.json` are in the run directory Rio prints. The JSON and HTML work offline.

## 5. Check the frontend's quality and delivery outcome

```sh
"$RIO" --artifact frontend --receipt frontend-record.json
```

Expect **exit 1** when the bundle SBOM contains entries without versions/package URLs.
A document can pass CycloneDX schema validation while failing these quality requirements.
Rio retains the failure and blocks delivery; it does not invent missing coordinates.

```sh
"$RIO" record inspect --file frontend-record.json
"$RIO" record report --file frontend-record.json --output frontend-report.html
python3 "$DEMO_SCRIPT" status "$DEMO"
```

Compare the reports: backend **passed / accepted**, frontend **failed checks / not
attempted**. Read the actual finding count in your receipt. If a future dependency or
generator resolution produces a complete frontend SBOM, it can pass and be delivered;
that is a valid result, not something to conceal or force into a failure.

To repeat a Rio command, choose a new receipt filename. Each execution has its own
run directory; another successful backend run uploads again. Bare `rio` selects both
inputs, so any enforced frontend failure blocks the whole selected batch.

## 6. Stop the receiver

```sh
python3 "$DEMO_SCRIPT" stop "$DEMO"
```

This removes only this demo's receiver containers, network and database volumes.
The builder removes itself after the build. Source, lockfiles, configuration and
reports stay in `$DEMO`. You can still inspect receipts with the receiver gone.
Use a fresh `$DEMO` directory to start again. If receiver setup fails, run this same
stop command before retrying; source-build failures are explained in `build.log`.
